# Writing a Pi worker

A worker is an ordinary Lambda program compiled with `--input --data`.  Keep the
protocol layer in three pieces: the generated schema, the local operations, and
a dispatch loop.  Pi owns processes, channels, retries, and deadlines; the worker
owns one state and one request at a time.

## Minimal shape

```lambda
include "pi_worker.lambda"
include "pi_schema_HeatCell.lambda"

; local operation: no channels, no retries, no I/O
heat-next → (λ u: Float halo: ArrayF.
  (+ u (* 0.2 (- (+ (+ (+ (arrayf-get halo 0) (arrayf-get halo 1))
                          (arrayf-get halo 2)) (arrayf-get halo 3))
                    (* 4.0 u))))))

; dispatch: one branch per op, using the generated names
cell-loop → (λ z: Int u: Float.
  hd → (pi-next-call 0)
  corr → (arrayi-get hd 0)
  if (< corr 0)
  then 0
  else
    op → (arrayi-get hd 1)
    nargs → (arrayi-get hd 2)
    a → (pi-read-floats (arrayf nargs 0.0) 0 nargs)
    if (== op op-init)
    then
      w → (pi-reply-ok corr (pi-empty))
      (cell-loop 0 (arrayf-get a 0))
    else if (== op op-step)
    then
      u2 → (heat-next u a)
      w → (pi-reply-ok corr (pi-vals1 u2))
      (cell-loop 0 u2)
    else if (== op op-snapshot)
    then
      w → (pi-reply-ok corr (pi-vals1 u))
      (cell-loop 0 u)
    else
      w → (pi-reply-err corr error-unknown_op 0 0 (- 0 1))
      (cell-loop 0 u))

hello → (pi-hello schema-hi schema-lo 2)
(cell-loop 0 0.0)
```

`pi_schema_<Protocol>.lambda` is generated by `pi build` and contains:

```lambda
schema-hi → …            ; 128-bit schema hash, two i64 words
schema-lo → …
op-init → 0              ; declaration-order index
op-step → 1
error-unknown_op → 10001
```

Use the names, not the numbers.  The schema hash covers the protocol signature,
not the constants, so changing a worker comment does not invalidate it.

## Request and reply

The transport is deliberately small:

* request: `corr`, `op`, `nargs`, then `nargs` Floats (stdin lines);
* reply: one `LMB1` f64 frame whose first value is `0` (Ok), `1` (Ok+stats), or
  `2` (Err);
* HELLO: one i64 frame `[schema_hi, schema_lo, version]`.

`pi_worker.lambda` provides:

| helper | purpose |
| --- | --- |
| `pi-next-call` | read `[corr, op, nargs]`, or `corr < 0` at EOF |
| `pi-read-floats` | read `nargs` Float arguments into an `ArrayF` |
| `pi-reply-ok` | `Ok(vals)` |
| `pi-reply-stats` | `Ok(vals, stats)` |
| `pi-reply-err` | `Err(code, span, sym)` |
| `pi-hello` | schema handshake |
| `pi-empty`, `pi-vals1`, `pi-vals2` | tiny payload constructors |

## Rules of thumb

1. Do not consume the state until the operation has succeeded.  A failed step
   must leave the last good state intact so Pi's `resume` is sound.
2. Read arguments before branching; a branch that returns early still has to
   drain the request body.
3. Keep channels and retries out of the worker.  Halo exchange belongs to the Pi
   element, not the local operation.
4. Return `Err` for protocol-level failures; keep local numerical corrections
   local (clamp, renormalize) and report them only if the contract says so.
5. Annotate recursive loop parameters (`z: Int`, state types) — the boxed
   fallback is slower and changes ownership semantics.

The full worker in [`examples/workers/heat_cell.lambda`](../examples/workers/heat_cell.lambda)
is about 45 lines; the protocol layer is the dispatch loop only.
